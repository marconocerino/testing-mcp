# E2 Domain services with mock data

**Goal:** Build accounts, orders and predictions services on mock data, behind adapter interfaces so real providers can be plugged in later. Each service doubles as an agent tool.

**Depends on:** E0

## E2-S1 Accounts service

**Status:** To do

**User story:** As a user, I want to see all my accounts, balances and recent transactions, so that I know what funds I have to trade with.

**Description:** REST service with GET /accounts, GET /accounts/{id}/balance and GET /accounts/{id}/transactions. Data comes from a BankDataProvider interface; v1 ships a mock provider with realistic seed data. Later the open banking connector implements the same interface.

**Acceptance criteria**

- [ ] Endpoints return accounts, balances (with currency and as-of timestamp) and paginated transactions.
- [ ] All responses follow a documented, normalized schema independent of any bank or aggregator.
- [ ] The mock provider has at least 3 users with 2-5 accounts each and 90 days of transactions.
- [ ] Every request is scoped to the authenticated user; requesting another user's account returns 403.
- [ ] OpenAPI spec is published and contract tests run in CI.

## E2-S2 Orders service (paper trading)

**Status:** To do

**User story:** As a user, I want to submit buy and sell orders and see their status, so that I can trade from the app.

**Description:** POST /orders/preview, POST /orders, GET /orders, DELETE /orders/{id}. Preview validates and returns cost, fees and warnings without placing anything. v1 executes against a paper-trading engine only.

**Acceptance criteria**

- [ ] Preview returns estimated cost, fees, resulting position and any validation warnings, and places nothing.
- [ ] Place requires a valid preview id less than 2 minutes old; otherwise it is rejected.
- [ ] Server-side validation rejects unknown instruments, quantity at or below zero, insufficient funds and out-of-hours market orders, each with a clear error code.
- [ ] Every order request carries an idempotency key; a repeated key never creates a second order.
- [ ] Order states (pending, filled, partially filled, cancelled, rejected) are queryable.
- [ ] No real broker or exchange connection exists in this epic.

## E2-S3 Market data and holdings service

**Status:** To do

**User story:** As a user, I want current prices and my holdings, so that I can judge positions before trading.

**Description:** GET /instruments/search, GET /quotes/{symbol}, GET /holdings, backed by a mock market data provider with simulated price movement.

**Acceptance criteria**

- [ ] Quotes include price, change, change percent, currency and timestamp.
- [ ] Holdings show quantity, average cost, market value and unrealised P&L.
- [ ] Instrument search returns matches by symbol or name within 300 ms on mock data.
- [ ] Provider interface allows swapping to a real data feed without API changes.

## E2-S4 Predictions service

**Status:** To do

**User story:** As a user, I want to see model-based predictions for instruments I hold or watch, so that I have extra context for decisions.

**Description:** GET /predictions/{symbol} returns a forecast with a confidence range, horizon, model version and generated-at time. v1 uses a placeholder model with clearly synthetic output.

**Acceptance criteria**

- [ ] Each prediction includes value, low/high range, horizon, model version and timestamp.
- [ ] Every response includes a disclaimer field whose text is approved by compliance (E7).
- [ ] Predictions are never returned without the range and disclaimer.
- [ ] The service is read-only and cannot create orders.

## E2-S5 Agent tool definitions for domain services

**Status:** To do

**User story:** As an agent developer, I want each read and preview operation exposed as a typed tool, so that the agent and the MCP server can call them.

**Description:** Define tools such as get_accounts, get_transactions, get_holdings, get_quote, get_prediction and prepare_order. prepare_order calls preview only.

**Acceptance criteria**

- [ ] Each tool has a name, description and input/output JSON schema generated from the OpenAPI spec.
- [ ] No tool can place, modify or cancel an order; placement exists only in the user-confirmed UI flow.
- [ ] Tools run with the calling user's identity; there is no service-account shortcut to user data.
- [ ] Tool definitions are shared by the agent service (E5) and the MCP server (E8).
