# E1 A2UI component catalog on the internal Angular library

**Goal:** Turn the internal Angular component library into an A2UI catalog so every generated or hand-written screen renders only with company-approved components. The catalog is the contract between the agent and the UI.

**Depends on:** E0

## E1-S1 Select the catalog components

**Status:** In review (2026-11-24). Draft list of 15 types in [docs/catalog-v1.md](../catalog-v1.md), checked by `frontend/src/app/catalog/catalog-v1.spec.ts`. Every type is mapped to a library component from the inventory. Selectors filled with Angular Material (stand-in). Waiting on: the sign-off.

**User story:** As a tech lead, I want an agreed list of 10-15 components for v1, so that the catalog stays small enough for the model to use well.

**Description:** Review the internal library with the design owner. Pick the components the trading screens need, for example Card, Row, Column, Text, Button, TextField, NumberField, Select, Table, Chart, Tabs, Badge, Alert and Divider.

**Acceptance criteria**

- [x] The v1 list names each component, its internal library selector and the A2UI type name it maps to. *(Selectors are Angular Material, the stand-in, by product owner decision; swap for the real library's when its typings are available.)*
- [x] Each component has a one-line purpose description written for the model ("Use Table for lists of 5+ comparable items").
- [x] Components needing complex inputs (templates, callbacks, content projection) are flagged with an adapter approach.
- [ ] The list is signed off by the tech lead and the library's design owner.

## E1-S2 Component adapter pattern

**Status:** Done (2026-11-24). Base class `frontend/src/app/catalog/adapter.ts`, reference adapters Card and Button, guide in [docs/adapters.md](../adapters.md), tests in `frontend/src/app/catalog/adapters.spec.ts`.

**User story:** As a developer, I want a standard adapter that wraps an internal component as an A2UI catalog component, so that adding a component is repetitive, not bespoke.

**Description:** Build the base adapter on @a2ui/angular's catalog extension mechanism. It maps A2UI props to the internal component's inputs, resolves data bindings, renders children by id and dispatches actions.

**Acceptance criteria**

- [x] One reference adapter (Card) is implemented and documented as the template for the rest.
- [x] Props flow from the A2UI data model to component inputs and update reactively when data changes.
- [x] Child components render inside the parent where the internal component expects content.
- [x] User interactions emit A2UI actions with the action name and payload; no direct service calls from adapters.
- [x] Unit tests cover prop mapping, data binding and action dispatch.

## E1-S3 Implement the v1 adapters

**Status:** Done (2026-11-24). All 15 types registered in `frontend/src/app/catalog/catalog.ts`; our schemas in `schemas.ts`; one `ui-*` stand-in wrapper per library component in `frontend/src/ui/stand-in/`. `OrderTicket` is a locked placeholder that shows its pre-fill values; E4-S4 adds the flow.

**User story:** As a developer, I want adapters for every v1 component, so that screens can use the full catalog.

**Description:** Implement the remaining adapters from E1-S1 using the E1-S2 pattern.

**Acceptance criteria**

- [x] Every component on the v1 list has an adapter, registered under its A2UI type name.
- [x] Each adapter has unit tests for its required props, optional props and actions.
- [x] Styling comes only from the internal library (no custom CSS overriding brand styles). *(Adapters have no CSS. The stand-in theme styles only the `ui-*` wrappers, on Material tokens, and fixes success and warning colours that Material lacks.)*
- [x] Accessibility attributes from the internal library (labels, roles, focus) are preserved.

## E1-S4 Catalog schema with model-facing descriptions

**Status:** To do

**User story:** As an agent developer, I want a machine-readable schema of the catalog, so that the same definition validates specs and instructs the model.

**Description:** Define each component's props in one schema source (JSON Schema or Zod) with descriptions, allowed values and defaults. Export it for the agent prompt, for server-side validation and for the MCP tool definitions.

**Acceptance criteria**

- [ ] One schema source generates both the validator and the model-facing catalog description.
- [ ] Every prop has a type, description and, where relevant, an enum of allowed values.
- [ ] A spec using an unknown component, unknown prop or wrong type fails validation with a readable error.
- [ ] Schema version is included in exported artifacts and checked at render time.

## E1-S5 Catalog gallery page

**Status:** Done (2026-11-25), except visual regression in CI (there is no CI). Page at `/dev/catalog` (`frontend/src/app/dev/catalog-gallery/`), samples in `samples/*.json`, tests in `catalog-gallery.page.spec.ts` and `app.spec.ts`.

**User story:** As a developer or designer, I want a page that renders every catalog component from sample A2UI specs, so that we can see and test the catalog without the agent.

**Description:** A dev-only route that lists each component with 2-3 sample specs (default, edge case, error state) loaded from JSON files.

**Acceptance criteria**

- [x] Every v1 component appears with at least two sample specs. *(Three each: default, edge case and invalid. A test fails if a catalog type has no sample file.)*
- [x] Editing a sample JSON file and reloading shows the change. *(Under `npx ng serve`; checked in headless Chrome.)*
- [x] Invalid samples show the validation error instead of a broken render.
- [ ] Visual regression snapshots run in CI for the gallery. *(Not done: CI was removed on 2026-11-23, see docs/decisions.md.)*
