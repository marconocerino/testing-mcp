# E5 Generative agent service and CopilotKit integration

**Goal:** Add the agent that turns user requests into A2UI specs, running on the internal LLM platform and connected to the Angular app through a self-hosted CopilotKit runtime. Built as a standalone service so E8 can reuse it.

**Depends on:** E4

## E5-S1 Agent service skeleton

**Status:** Done (2026-11-25). `services/agent-service` (Node/TypeScript): `generate_view` served as an AG-UI agent at `POST /agent`, calling Groq (`openai/gpt-oss-120b`). Tested with a scripted model and live against Groq.

**User story:** As a developer, I want a standalone agent service with a generate_view entry point, so that both the web runtime and the MCP server can call it.

**Description:** Service that takes a user request plus context (user id, current view, saved layout) and returns a stream of A2UI messages. It calls the internal LLM with the catalog description, example specs (E4-S6) and domain tools (E2-S5).

**Acceptance criteria**

- [x] generate_view accepts a request and context and streams A2UI messages. *(AG-UI `RunAgentInput` in; `a2ui.message` custom events out.)*
- [x] The LLM endpoint, model and credentials are configuration, not code. *(`LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`.)*
- [x] The service has no browser-facing endpoint; it is reached only through the CopilotKit runtime or the MCP server. *(No CORS and no published port in compose.)*
- [x] Each run has a trace id propagated to logs and tool calls. *(The AG-UI run id is the trace id: in every JSON log line and the `X-Trace-Id` header. No tool calls yet.)*

## E5-S2 Prompt, catalog and examples

**Status:** In progress (2026-11-25). The prompt is built in `services/agent-service/src/prompt.ts` from the catalog export, the data paths and the action allow-list, with one inline example. Hand-authored example specs (E4-S6) and the eval suite (E7-S4) don't exist yet.

**User story:** As an agent developer, I want a versioned system prompt built from the catalog schema and example specs, so that output stays in our design language and is reproducible.

**Acceptance criteria**

- [ ] The prompt is assembled from the E1-S4 catalog export and E4-S6 examples, not hand-copied. *(Catalog export: yes. E4-S6 examples: not yet, one inline example instead.)*
- [ ] Prompt version is stored with every generated spec. *(`PROMPT_VERSION` is in every log line of the run, keyed by trace id; not stored with saved views yet (E6).)*
- [x] The prompt instructs the model to bind data by path, never to invent figures, and to use OrderTicket for any trading intent.
- [ ] ~~Changing the prompt triggers the eval suite (E7-S4) in CI.~~ *(No CI, decision 2026-11-23. Needs E7-S4 first; then run it locally.)*

## E5-S3 Validation and repair loop

**Status:** In progress (2026-11-25). Validation, one repair attempt and a safe fallback are in `services/agent-service/src/generate-view.ts` and `validate.ts`; the client validates again (E3-S4).

**User story:** As a user, I want generated screens to always render correctly, so that I never see a broken page.

**Description:** Validate every generated spec against the catalog schema. On failure, send the validation errors back to the model once for repair; if that fails, fall back to the nearest hand-authored spec.

**Acceptance criteria**

- [x] No spec reaches the client without passing validation. *(Catalog JSON Schemas (with formats), structure, action allow-list.)*
- [x] At most one repair attempt per request; total added latency is logged. *(`repairMs` in the `view.generated` / `view.fallback` log events.)*
- [ ] On final failure the user sees a relevant hand-authored screen and a short notice, not an error. *(For now a generic EmptyState and a short reply; relevant hand-authored screens need E4-S6.)*
- [ ] Validation failure rate is reported as a metric (E7-S5). *(Logged as `view.invalid` / `view.fallback` events; no metrics system yet.)*
