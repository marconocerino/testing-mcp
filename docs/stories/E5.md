# E5 Generative agent service and CopilotKit integration

**Goal:** Add the agent that turns user requests into A2UI specs, running on the internal LLM platform and connected to the Angular app through a self-hosted CopilotKit runtime. Built as a standalone service so E8 can reuse it.

**Depends on:** E4

## E5-S1 Agent service skeleton

**Status:** To do

**User story:** As a developer, I want a standalone agent service with a generate_view entry point, so that both the web runtime and the MCP server can call it.

**Description:** Service that takes a user request plus context (user id, current view, saved layout) and returns a stream of A2UI messages. It calls the internal LLM with the catalog description, example specs (E4-S6) and domain tools (E2-S5).

**Acceptance criteria**

- [ ] generate_view accepts a request and context and streams A2UI messages.
- [ ] The LLM endpoint, model and credentials are configuration, not code.
- [ ] The service has no browser-facing endpoint; it is reached only through the CopilotKit runtime or the MCP server.
- [ ] Each run has a trace id propagated to logs and tool calls.

## E5-S2 Prompt, catalog and examples

**Status:** To do

**User story:** As an agent developer, I want a versioned system prompt built from the catalog schema and example specs, so that output stays in our design language and is reproducible.

**Acceptance criteria**

- [ ] The prompt is assembled from the E1-S4 catalog export and E4-S6 examples, not hand-copied.
- [ ] Prompt version is stored with every generated spec.
- [ ] The prompt instructs the model to bind data by path, never to invent figures, and to use OrderTicket for any trading intent.
- [ ] Changing the prompt triggers the eval suite (E7-S4) in CI.

## E5-S3 Validation and repair loop

**Status:** To do

**User story:** As a user, I want generated screens to always render correctly, so that I never see a broken page.

**Description:** Validate every generated spec against the catalog schema. On failure, send the validation errors back to the model once for repair; if that fails, fall back to the nearest hand-authored spec.

**Acceptance criteria**

- [ ] No spec reaches the client without passing validation.
- [ ] At most one repair attempt per request; total added latency is logged.
- [ ] On final failure the user sees a relevant hand-authored screen and a short notice, not an error.
- [ ] Validation failure rate is reported as a metric (E7-S5).

## E5-S4 CopilotKit runtime integration

**Status:** To do

**User story:** As a developer, I want the CopilotKit runtime to host the agent with A2UI enabled, so that the Angular app gets chat and streaming without custom plumbing.

**Description:** Deploy @copilotkit/runtime (self-hosted) with the agent registered and A2UI enabled on the runtime. Point HttpTransport (E3-S3) at it. No CopilotKit cloud services or keys.

**Acceptance criteria**

- [ ] The runtime runs on company infrastructure; no traffic goes to CopilotKit or other external services.
- [ ] A2UI is enabled on the runtime and the client, and /info reports it.
- [ ] The Angular app receives A2UI surfaces through the runtime and renders them with the E1 catalog.
- [ ] Runtime authentication validates the user's SSO token on every request.

## E5-S5 Chat panel

**Status:** To do

**User story:** As a user, I want to ask for views in plain language, so that I can shape the app to what I need.

**Description:** Add the CopilotKit chat component in the shell's panel (E3-S1). Generated surfaces render in the main region or inline in chat, depending on the response.

**Acceptance criteria**

- [ ] A request like "show my accounts as a compact table with this month's spending" produces a matching surface within 10 s at p95.
- [ ] The user can ask follow-ups that modify the current view ("add predictions for my top 3 holdings").
- [ ] Trading requests ("buy 10 shares of X") open a pre-filled OrderTicket; nothing is placed without the confirm step.
- [ ] Chat styling follows the internal library's theme.

## E5-S6 Agent-callable actions from generated UI

**Status:** To do

**User story:** As a user, I want buttons in generated views to work, so that the generated UI is usable, not just a picture.

**Acceptance criteria**

- [ ] Actions from generated components go through the E3-S4 action router.
- [ ] Actions either trigger an allow-listed client handler or are sent to the agent as a follow-up event.
- [ ] Actions with financial effect (place, cancel, transfer) are never available to generated specs; only the locked OrderTicket can trigger them.
