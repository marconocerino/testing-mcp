# E7 Trading safety, compliance and observability

**Goal:** Hard limits on what generated UI can do, audit trails, compliance wording, agent evals and monitoring. Runs alongside E2 to E6.

**Depends on:** Runs alongside E2 to E6

## E7-S1 Order safety guardrails

**Status:** To do

**User story:** As a compliance officer, I want orders to be impossible without explicit user confirmation and server-side checks, so that the AI can never trade on a user's behalf.

**Acceptance criteria**

- [ ] Order placement is reachable only from the locked OrderTicket confirm step (E4-S4).
- [ ] Agent tools and generated specs have no path to place, modify or cancel orders; this is covered by automated tests.
- [ ] Server enforces per-user limits (max order value, daily count) configurable by operations.
- [ ] A penetration-style test attempts to trigger placement from a crafted spec and a crafted prompt; both fail.

## E7-S2 Audit logging

**Status:** To do

**User story:** As a security officer, I want an immutable record of orders and AI-generated views, so that we can investigate any incident.

**Acceptance criteria**

- [ ] Every order preview, placement and cancellation is logged with user, timestamp, values and trace id.
- [ ] Every generated spec is logged with user, prompt, prompt version, model version and validation result.
- [ ] Logs go to the company audit store with the agreed retention period.
- [ ] Logs contain no access tokens or full account numbers.

## E7-S3 Compliance content and disclosures

**Status:** To do

**User story:** As a compliance officer, I want approved wording on AI-generated content and order screens, so that users aren't misled.

**Acceptance criteria**

- [ ] Disclaimer text (AI-generated content, paper trading) is approved and stored centrally, not in specs.
- [ ] Generated views carry a visible "AI-generated layout" indicator.
- [ ] The investment-advice classification from E0-S4 is resolved, and any resulting requirements are added as stories.
- [ ] The agent prompt forbids recommendations to buy or sell; an eval case checks this.

## E7-S4 Agent evaluation suite

**Status:** To do

**User story:** As an agent developer, I want an automated eval suite, so that prompt or model changes don't silently degrade quality.

**Description:** A set of at least 50 test requests with expected properties (valid spec, right components, correct bindings, no invented numbers, OrderTicket for trading intent, no advice).

**Acceptance criteria**

- [ ] The suite runs in CI on any change to the prompt, catalog or model configuration.
- [ ] Reports validity rate, property pass rate and p50/p95 latency.
- [ ] Merge is blocked if validity drops below 98% or any safety case fails.
- [ ] Results are stored so trends can be compared across versions.

## E7-S5 Monitoring and alerting

**Status:** To do

**User story:** As an on-call engineer, I want dashboards and alerts for the agent and services, so that problems are caught before users report them.

**Acceptance criteria**

- [ ] Dashboards show request rate, error rate, generation latency, validation failure rate, repair rate and fallback rate.
- [ ] Alerts fire when validation failure rate exceeds 5% or p95 generation latency exceeds 15 s over 10 minutes.
- [ ] Traces link a user request through the runtime, agent, LLM call and tool calls.

## E7-S6 Security review of the data flow

**Status:** To do

**User story:** As a security officer, I want a formal review before real data is connected, so that the app meets company standards.

**Acceptance criteria**

- [ ] Threat model covers prompt injection (including from transaction descriptions), data leakage and spec tampering.
- [ ] Mitigations are implemented or tracked as stories.
- [ ] Written security sign-off exists before any real bank or market data is connected.
