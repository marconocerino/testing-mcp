# E4 Hand-authored A2UI screens

**Goal:** Deliver the full app from A2UI specs written by the team, with no AI involved. Proves the catalog end to end and produces the example specs the agent learns from.

**Depends on:** E1, E2, E3

## E4-S1 Data binding between specs and services

**Status:** To do

**User story:** As a developer, I want specs to reference live data by path instead of embedding values, so that layouts stay static while data refreshes.

**Description:** Define how a spec binds to domain data (for example /accounts, /holdings) using the A2UI data model. A data loader fetches the bound sources via the domain APIs and pushes updates into the surface.

**Acceptance criteria**

- [ ] Specs contain bindings, not hard-coded account or price values.
- [ ] Changing underlying data updates the rendered components without re-sending the component tree.
- [ ] Unknown binding paths fail validation with a clear error.
- [ ] Data refresh intervals are configurable per source (for example quotes every 5 s, accounts on load).

## E4-S2 Dashboard screen

**Status:** To do

**User story:** As a user, I want a dashboard showing total balance, holdings and today's movers, so that I get an overview at a glance.

**Acceptance criteria**

- [ ] Shows total balance across accounts, a holdings table and a top-movers list, all from catalog components.
- [ ] Values update from the data model without a page reload.
- [ ] Empty states (no accounts, no holdings) show an internal-library empty-state component with a next step.
- [ ] Spec is stored as a versioned JSON file in the repo.

## E4-S3 Accounts and transactions screen

**Status:** To do

**User story:** As a user, I want to browse my accounts and their transactions, so that I can check my cash position.

**Acceptance criteria**

- [ ] Lists all accounts with name, type, balance and currency.
- [ ] Selecting an account shows paginated transactions with date, description, amount and running balance.
- [ ] Transactions can be filtered by date range using catalog field components.
- [ ] Selection and filtering are A2UI actions handled by allow-listed handlers.

## E4-S4 Order ticket flow

**Status:** To do

**User story:** As a user, I want to prepare, preview and confirm an order, so that I can trade safely.

**Description:** A fixed, three-step OrderTicket flow: enter (instrument, side, quantity, type), preview (cost, fees, warnings from POST /orders/preview), confirm (explicit button, then POST /orders).

**Acceptance criteria**

- [ ] An order can only be placed from the confirm step, by an explicit user click on the confirm button.
- [ ] The confirm step shows the exact preview values; if inputs change, a new preview is required.
- [ ] Validation errors from the server appear next to the relevant field.
- [ ] After placement the user sees the order id and status, and the order appears in the orders list.
- [ ] The OrderTicket spec is locked: E5 may pre-fill its fields but cannot alter its structure or actions.

## E4-S5 Predictions screen

**Status:** To do

**User story:** As a user, I want to see predictions for my holdings and watchlist, so that I have more context for decisions.

**Acceptance criteria**

- [ ] Each prediction shows value, range, horizon and model date in a chart or card.
