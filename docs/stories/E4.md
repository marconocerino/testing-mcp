# E4 Hand-authored A2UI screens

**Goal:** Deliver the full app from A2UI specs written by the team, with no AI involved. Proves the catalog end to end and produces the example specs the agent learns from.

**Depends on:** E1, E2, E3

## E4-S1 Data binding between specs and services

**Status:** In progress (2026-11-27). Specs bind by path and every view (default or generated) gets the data model from `SURFACE_DATA`, still the frontend mock dataset until E2's services exist.

**User story:** As a developer, I want specs to reference live data by path instead of embedding values, so that layouts stay static while data refreshes.

**Description:** Define how a spec binds to domain data (for example /accounts, /orders) using the A2UI data model. A data loader fetches the bound sources via the domain APIs and pushes updates into the surface.

**Acceptance criteria**

- [x] Specs contain bindings, not hard-coded account or price values. *(A test checks the spec files contain no balances from the data.)*
- [x] Changing underlying data updates the rendered components without re-sending the component tree.
- [ ] Unknown binding paths fail validation with a clear error.
- [ ] Data refresh intervals are configurable per source (for example order status every 5 s, accounts on load).

## E4-S2 Dashboard screen

**Status:** Done on mock data (2026-11-27). `frontend/src/app/screens/specs/dashboard.json`, the default tab at `/dashboard`.

**User story:** As a user, I want a dashboard showing total balance, my accounts and my recent orders, so that I get an overview at a glance.

**Acceptance criteria**

- [x] Shows total balance across accounts, an accounts summary and a recent-orders list with status, all from catalog components. *(Plus cash and invested tiles, and "View all" links to the Accounts and Orders tabs.)*
- [x] Values update from the data model without a page reload.
- [x] Empty states (no accounts, no orders) show an internal-library empty-state component with a next step. *(Declared in the spec (`emptyStates`) and applied when the view loads; a list emptied later is not swapped.)*
- [x] Spec is stored as a versioned JSON file in the repo.

## E4-S3 Accounts and transactions screen

**Status:** Done on mock data (2026-11-27). `frontend/src/app/screens/specs/accounts.json` at `/accounts`; handlers in `frontend/src/app/screens/screen-actions.ts`.

**User story:** As a user, I want to browse my accounts and their transactions, so that I can check my cash position.

**Acceptance criteria**

- [x] Lists all accounts with name, type, balance and currency.
- [x] Selecting an account shows paginated transactions with date, description, amount and running balance. *(The first account is selected when the tab opens; 10 rows per page.)*
- [x] Transactions can be filtered by date range using catalog field components. *(Two DateFields (From, To).)*
- [x] Selection and filtering are A2UI actions handled by allow-listed handlers. *(`selectAccount`, `applyTransactionFilter`, `goTo`: client handlers, not agent calls.)*

## E4-S4 Order ticket flow

**Status:** To do

**User story:** As a user, I want to prepare, preview and confirm an order, so that I can trade safely.

**Description:** A fixed, three-step OrderTicket flow: enter (instrument, side, quantity, type), preview (cost, fees, warnings from POST /orders/preview), confirm (explicit button, then POST /orders).

**Acceptance criteria**

- [ ] An order can only be placed from the confirm step, by an explicit user click on the confirm button.
- [ ] The confirm step shows the exact preview values; if inputs change, a new preview is required.
- [ ] Validation errors from the server appear next to the relevant field.
- [ ] After placement the user sees the order id and status, and the order appears in the orders list.
- [ ] The OrderTicket spec is locked: E5 may pre-fill its fields but cannot alter its structure or actions.

## E4-S6 Spec library for agent examples

**Status:** In progress (2026-11-27). The dashboard, accounts and orders specs carry a description of what they show and when to use them; not yet fed to the agent prompt.

**User story:** As an agent developer, I want the hand-authored specs curated as an example library, so that the agent produces screens in the same style.

**Acceptance criteria**

- [x] Each screen spec has a short natural-language description of what it shows and when to use it. *(For the three default views.)*
- [ ] Specs pass validation in CI.
- [ ] At least 6 example specs exist covering dashboard, accounts, transactions, orders list, order ticket and an empty state.
